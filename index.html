crazyflie-behavior

Hide-and-seek drone

A Crazyflie nano drone that plays hide-and-seek with a small child, built with techniques from game NPCs: a map of the room, hiding-spot selection and line-of-sight checks, on a robot whose sensors are noisy and whose position drifts.

While the child waits behind a gate, the drone flies off, lands behind a wall and turns its motors off. The child hunts for it, helped by a flash-and-chirp hint every 15 seconds. When they pick it up, it lights up and the computer plays a fanfare.

Design decisions

  • Safe because of how the game works

    The drone flies only while the play area is empty, then lands and stops its motors before the search begins. A child only ever meets a drone with its motors off.

    ADR-0016

  • One narrow path to the motors

    Only the safety layer commands the drone. The operator's kill switch is the single exception: it can only cut the motors, and it runs on its own thread so it still works if the tick loop hangs.

    ADR-0008 · 0013

  • It always lands

    Touchdown counts only on a steady downward range reading. Without one, a slow final descent continues until a time limit, so a failing sensor can't cut the motors in mid-air.

    ADR-0012 · 0019

  • Game instincts, robot rules

    A game keeps playing and logs the failure. Here, a failure that leaves flight safe is logged and worked around, and one that makes flight unsafe makes the drone fail safe.

    ADR-0020

  • Hardware behind an interface

    Behavior code talks only to a drone interface, so the same logic runs against a mock, a simulator or the real Crazyflie, on a 20 Hz tick loop with a swappable clock for tests.

    ADR-0002 · 0009 · 0023

Every design decision is written up with the options considered, 28 records so far. I set the goals and make the calls; implementation is AI-assisted, and each record notes whose idea it was. Formatting, lint, strict type checks and tests, including architecture rules enforced as tests, run on every push.

GenevaEngine

Geneva Engine

A custom C++ engine built from scratch for physics-driven games, where the gameplay comes from mechanical constructions like soft bodies and linkages.

The core problems are the ones robots have too: a fixed-rate update loop, rigid-body physics, and state machines that turn commands into motion.

  • Fixed-timestep loop

    Input, physics, gameplay, render. Physics steps at a fixed 100 Hz with an accumulator, so the simulation behaves the same at any frame rate.

    Core/GameSession.cpp

  • Entities and constructs

    An entity owns a construct, a composite of Box2D bodies and joints. Player and AI commands arrive through one path, so either can drive any construct.

    Constructs/Construct.hpp

  • Templated state machines

    Behavior runs on a State<T> finite-state machine. The soft-body character switches between grounded and airborne states.

    Core/State.hpp

  • Soft-body character

    What looks like a box is five circles held together by joints, moved and jumped by forces applied to the center body.

    Constructs/SoftBox.cpp
